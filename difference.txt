NSF REU custom simulator: what changed
=======================================

This version keeps the original warehouse simulation behavior while making the
experiment easier to run, repeat, compare, and inspect.  The main program now
uses the modular project workflow, but it still relies on the tested original
movement and visualization code internally so that robot behavior is preserved.

Main differences from the older version
----------------------------------------

* The project has one normal way to start the simulator: `main.py`.
* The project is organized into smaller areas for the map, robots, sensing,
  trust, defense methods, attacks, scenario setup, and data collection.
* A scenario can be saved before a run.  This saves the map, robot starting
  positions, delivery tasks, temporary obstacles, attack times, and phase times.
  Every defense method can then be tested on exactly the same situation.
* The comparison command runs the four main methods together:
  `full_trust`, `majority_vote`, `trust_fused`, and `source_linked`.
* `soft_probability` is still available and can be run separately using the
  same saved scenario.
* The simulator now records more useful results, including deliveries completed,
  no-path steps, movement steps, distance traveled, replans, blocked moves,
  trust changes, and contradictions.
* Results are saved in easy-to-read CSV files instead of being available only in
  the terminal.
* The default map is the warehouse map from the linked GitHub project.  The
  attacker escape route is kept open so it does not get trapped at the top-left
  checkpoint area.
* Fake obstacles are placed with checks so they do not appear directly under
  another robot.  They may still appear next to a robot.
* The old standalone comparison and audit helper scripts were removed.  Generated
  results, caches, editor files, and temporary files are ignored by Git.

There is still one important transition detail: the modular workflow uses the
tested original movement, planning, fusion, and visualization code internally.
This was kept intentionally because replacing it all at once could change the
experiment results.  A future project step could move those pieces completely
into the modular files, but that is not part of this cleanup.

First-time setup from GitHub
----------------------------

    git clone https://github.com/natchuop/custom_map_poisoning_costmap.git
    cd custom_map_poisoning_costmap
    python install_dependencies.py --install --include-dev

A virtual environment is recommended, but not required.  Check the installation
and run the tests with:

    python install_dependencies.py --skip-gui
    python -m pytest -q

Run one simulation
------------------

    python main.py --headless --no-animation --seed 10 --defense-method source_linked --output-directory outputs/seed10_source

For the normal visual run, leave out `--headless --no-animation`.  The window will
show the animation, heatmap, and graphs.

Each output folder contains the main files:

* `run_summary.csv` — one-row summary of the run.
* `events.csv` — attacks, reports, trust changes, replans, and other events.
* `robot_timeseries.csv` — robot positions and running totals over time.
* `scenario_manifest.json` — the exact situation that was run.
* `audit_report.json` — checks that the saved scenario is valid.

Run multiple methods on the same situation
-------------------------------------------

First save a scenario:

    python main.py --headless --manifest-only --seed 10 --no-animation --output-directory outputs/seed10_manifest

Then compare the four main methods:

    python main.py --headless --compare --seed 10 --no-animation --manifest outputs/seed10_manifest/scenario_manifest.json --output-directory outputs/seed10_compare

The comparison folder contains one folder for each method.  To also run
`soft_probability` on that same scenario:

    python main.py --headless --seed 10 --no-animation --manifest outputs/seed10_manifest/scenario_manifest.json --defense-method soft_probability --output-directory outputs/seed10_compare/soft_probability

Important settings
------------------

* `--defense-method` chooses the method for one run.
* `--compare` runs the four main methods using one shared scenario.
* `--seed` chooses the repeatable random seed.
* `--attacks` chooses the attack types, separated by commas, or `none`.
* `--recon-steps`, `--attack-steps`, and `--recovery-steps` set the lengths of
  the three phases.
* `--max-steps` limits the total run length.
* `--deliveries-per-robot` sets the delivery workload.
* `--attack-interval-min` and `--attack-interval-max` control how often attacks
  are scheduled.
* `--no-animation` is useful for faster headless runs.

What is still unfinished
------------------------

These items are listed for future work and were not changed here:

* The project still uses the tested original robot/world code internally.  A
  completely independent modular replacement has not been finished.
* The default warehouse scenario currently creates fake-obstacle attacks.  The
  other attack types are available in the general scenario builder or in a saved
  manifest, but the default warehouse builder does not yet automatically create
  them from the `--attacks` selection.
* The visual interface does not expose every advanced command-line setting.
* Exact agreement with every historical experiment has not been established.
  For fair comparisons, use one saved scenario and keep all settings fixed.

Attack status
-------------

The project includes three attack types:

1. `fake_obstacle` — claims that a clear location is blocked.
2. `false_clearance` — claims that a temporarily blocked location is clear.
3. `stale_reassertion` — repeats a blockage claim after the real blockage has
   cleared.

The last two are implemented in the general scenario-building and validation
logic.  The default warehouse scenario currently schedules fake obstacles only,
so use a saved manifest or the general builder when you need to test the other
two attacks.
