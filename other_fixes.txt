Additional findings and fixes
==============================

Date: 2026-09-09
Scope: audit of the preserved pre-harmonization physical-AI results, plus a
short smoke run after the Room 32 authoring correction.

This file is supplemental to deliveries_plan_fix.txt. The delivery-plan fix is
the primary change for the no-path/stalled-delivery behavior. This file records
other issues that should be handled or explicitly controlled before treating a
new full suite as final. It does not silently change the delivery semantics,
trust values, unknown-cell cost, attack definitions, or method scoring.

Executive summary
-----------------

1. Confirmed methodology bug: the default map and Room 32 were not authoring
   attacks from the same frozen reconnaissance inputs. Room 32 used the
   generic author_manifest path, while the default warehouse path used the
   traffic-aware warehouse author. This has been corrected in
   map_poisoning/scenario.py. A new full suite is required; the old numbers
   must not be combined with the corrected numbers.

2. Attack dose is not equal across maps. The old suite used approximately the
   same number of attack events, but fake-obstacle claimed-cell totals differed
   substantially because candidate footprints and available geometry differ.
   This is a comparability issue, not evidence that either map is broken.

3. Traffic diagnostics expose unresolved deadlock episodes. In the preserved
   results, 33 of 177 saved runs had deadlocks_detected different from
   deadlocks_recovered. There were no robot-overlap violations, so this is not
   a collision-safety failure. It means the current traffic controller can
   detect a deadlock and fail to complete its yield/recovery path, leaving an
   active blocked episode until the run ends. The delivery-plan fix addresses
   the main no-path case; the additional diagnostics below should still be
   added so unresolved traffic cycles are explicit rather than implicit.

4. The preserved full suite is not a valid final baseline. It was generated
   before the Room 32 harmonization and while the worktree was dirty. The
   replacement full run was intentionally stopped after the user supplied the
   delivery-plan fix request; its fresh output directory currently contains
   only 12 completed cells. Do not aggregate those partial results as a full
   suite.


1. Room 32 reconnaissance/authoring mismatch -- CONFIRMED AND CORRECTED
-----------------------------------------------------------------------

Observed implementation difference

The warehouse/default path authored physical obstacles and attack candidates
using the traffic-aware, attack-free bootstrap/recon information. The generic
Room 32 path used a nominal route heatmap and generic placement/scoring logic.
Consequently, the two maps did not satisfy the same condition:

    attack placement = frozen attack-free reconnaissance traffic + static geometry

The old manifests showed different selection-basis labels:

    default fake:          frozen_reconnaissance_traffic_and_static_geometry
    Room 32 fake:          frozen_reconnaissance_routes_missions_and_static_geometry
    default false-clearance:
                            frozen_reconnaissance_traffic_plus_static_geometry_and_authored_physical_schedule
    Room 32 false-clearance:
                            frozen_reconnaissance_routes_missions_and_static_geometry

Why this matters

Nominal routes are not the same as the routes actually produced by the
reconnaissance rollout. Attack footprints can therefore target different
bottlenecks, receive different relevance scores, and create different belief
cuts even when the seed, phase lengths, attack interval, trust threshold, and
method are identical. This can make one map/method combination appear better
or worse for reasons unrelated to the defense method.

Correction already made

map_poisoning/scenario.py now:

  - runs an attack-free, physical-obstacle-free bootstrap rollout;
  - uses frozen reconnaissance traffic heatmaps for physical obstacle
    authoring on generic maps as well as the warehouse map;
  - builds the attack candidate pool from the frozen recon robot traces and
    heatmap;
  - uses the same frozen recon target-selection path for fake obstacles,
    false clearances, and stale reassertions;
  - refuses to fall back to nominal random fake-obstacle placement when an
    explicit recon candidate pool is empty, except for the documented
    no-delay candidate-construction fallback; and
  - records the same selection-basis labels in the manifest metadata.

Evidence after correction

The harmonized smoke run completed 48/48 run cells successfully:

    maps:       default, Room 32
    seeds:      1, 2
    attacks:    fake, false-clearance, mixed fake+false-clearance
    methods:    full_trust, majority_vote, source_memory, trust_fused
    steps:      300
    stale:      disabled
    plots:      54 aggregate PNGs and 624 per-run PNGs
    plot errors: 0

All six batch_validation.json files reported valid=true and 8/8 completed
cells. The smoke manifests use the same recon-based selection-basis labels on
both maps. This validates the authoring path, not the long-run delivery
outcomes; the full suite still needs to be rerun after the delivery-plan fix.

Required follow-up

After deliveries_plan_fix.txt is implemented, rerun the complete suite into a
new directory. Compare the new manifests before comparing deliveries:

  - same scenario_manifest_hash across the four methods for each map/seed/
    attack condition;
  - reference_step = recon_steps - 1;
  - heatmap_reference_steps = recon_steps;
  - no attack event before the attack phase;
  - stale_reassertion events absent when stale is disabled; and
  - identical config hashes within each treatment.


2. Unequal attack dose across maps -- COMPARABILITY FIX NEEDED
---------------------------------------------------------------

Evidence from the preserved pre-harmonization output

The old output contained 177 completed run summaries. Attack event counts were
similar, but claimed-cell totals were not:

    condition        map       mean events   mean fake/total claimed cells
    -----------------------------------------------------------------------
    fake             default       53.1              1200.7
    fake             Room 32       52.7               625.8
    false-clearance  default       52.6               214.9
    false-clearance  Room 32       52.6               254.8
    mixed             default       52.6               699.2 total

The Room 32 mixed condition was incomplete in the preserved output, so it
should not be used for a cross-map mean. These values are event/cell summaries,
not a claim that the attack generator is randomly malfunctioning.

Likely cause

Fake obstacles are footprints selected from map geometry and recon traffic.
Room 32 has fewer eligible recon-overlapping footprint cells and different
obstacle topology. Equal event intervals therefore produce unequal reported
area and likely unequal bottleneck coverage.

Why this should be fixed or reported

If the scientific question is "what happens under the configured attack
schedule," geometry-adaptive dosage is valid, but the reports must state that
the treatment is schedule-equal and cell-dose-unequal. If the question is a
fair map comparison, the treatment needs an explicit dose constraint.

Recommended implementation

  A. Keep the main security benchmark schedule-based, because silently
     changing its attack definition would change the experiment. Add the
     following per-condition/per-run metrics to the aggregate data:

       attack events authored
       report cells authored
       unique cells claimed
       footprint area mean/min/max
       recon traffic score and route-overlap count
       permanent versus temporary target counts

  B. Add a separately named balanced-dose benchmark, not a replacement for
     the main benchmark. It should use a documented target-cell budget or
     footprint-area distribution per map, with a deterministic shortage rule
     when the map cannot supply that dose.

  C. Do not compare only attack event counts when explaining map results. Plot
     deliveries/replans against both event dose and claimed-cell dose, or show
     the dose in the plot/table caption.

Acceptance check

For every final map/seed/attack condition, the aggregate report should expose
both event-level and cell-level attack load. A cross-map comparison should be
labelled either "schedule matched" or "dose matched".


3. Unresolved traffic deadlocks -- DIAGNOSTIC AND RECOVERY FIX NEEDED
---------------------------------------------------------------------

Observed result

Of the 177 saved pre-harmonization runs:

    33 runs: deadlocks_detected != deadlocks_recovered
     0 runs: robot_overlap_violations > 0
     0 runs: steps_completed != 3000

The mismatch appeared especially in Room 32 false-clearance runs. Examples
include Room 32 false-clearance seed 3 with full_trust at 9/7, majority_vote at
11/9, and source_memory at 10/8; seed 1 majority_vote was 3/0. The exact
delivery result from these old runs is not a clean post-fix benchmark, but the
counter pattern is a genuine controller/diagnostic concern.

Current mechanism

traffic_deadlock_detected creates an active deadlock ID after a wait threshold
or repeated joint state. A deadlock is counted as recovered only when the
robot later exits its yield state and emits traffic_deadlock_recovered for that
ID. If no legal parking/reverse-out route is found, the robot remains in the
active blocked condition and no recovery event is emitted. The summary code
correctly counts only paired recovery IDs; it is not inventing recoveries.

What to add beyond the delivery-plan fix

  - Add explicit unresolved_deadlocks and unresolved_deadlock_ids to the run
    summary.
  - Record one wait-for edge per blocked robot per episode, including blocker,
    requested cell, wait age, and current traffic mode.
  - Record whether a deadlock is a cycle, a stationary blocker, a no-parking
    geometry case, or a planner/no-path case.
  - Ensure an episode cannot be counted as recovered until all robots in the
    episode have returned to NORMAL or the episode is closed as unrecoverable.
  - Add a bounded retry/backoff so the same unresolved cycle does not generate
    unbounded duplicate replans or deadlock IDs.
  - At run end, close every active episode as either recovered or
    unrecoverable; never leave the status implicit.

This should remain method-neutral. Do not delete peer claims, lower unknown
costs, alter trust thresholds, or convert a no-path state into a delivery.
Those changes would bias the security comparison.

Suggested tests

  1. A two-robot head-on swap recovers and has zero overlap violations.
  2. A narrow corridor with no legal parking emits exactly one bounded
     unrecoverable episode rather than repeated detections.
  3. A temporary obstacle that invalidates a yield route closes the old
     episode and either repairs it or reports unrecoverable.
  4. Every deadlock ID in the summary is present in exactly one detected event
     and exactly zero or one terminal event.


4. Reproducibility and batch-integrity controls -- SHOULD FIX
--------------------------------------------------------------

The reporting code already marks a batch invalid when cells are failed or
missing, and it warns when runs come from a dirty worktree. The preserved
results were produced with a dirty worktree and the old full run was
interrupted. This is a provenance problem, not a simulator outcome.

Required controls for the next publishable run

  - Use a new output directory after the delivery-plan change; do not resume
    the pre-harmonization directory.
  - Require batch_validation.valid == true before calculating final means.
  - Require requested_cell_count == completed_cell_count and
    failed_cell_count == missing_cell_count == 0.
  - Record the exact commit, dirty flag, config hash, map hash, scenario
    manifest hash, and command line in the results index.
  - Keep partial/interrupted output directories clearly named as partial and
    exclude them from any combined report.
  - If the worktree is intentionally dirty during development, label the
    output exploratory and rerun from a clean commit for final figures.

The existing batch validator already detects most of this. The remaining
process fix is to make the analysis/reporting workflow refuse to pool invalid
or mixed-provenance output rather than relying on a human to notice the
warning.


5. Attack metrics and denominators -- REVIEWED; document, do not silently alter
--------------------------------------------------------------------------------

The current metric implementation has separate denominators:

  - *_report_cells_authored: all cells in authored events;
  - *_report_cells_delivered: malicious report cells received by a victim;
  - *_report_cells_accepted: delivered cells admitted by fusion;
  - *_report_cells_influential: delivered, accepted cells with positive
    operational weight;
  - *_event_acceptance_rate: number of attack events with at least one accepted
    report divided by authored event count.

This is internally consistent and should not be collapsed into one percentage.
In particular, event acceptance and cell acceptance answer different
questions. A false-acceptance rate of zero when no malicious report cell was
delivered is currently a reporting convention (the denominator is protected by
max(1, ...)); it should be accompanied by the delivered-cell denominator so a
zero cannot be mistaken for measured rejection.

Recommended reporting addition

Add an explicit status/denominator field to the aggregate tables, for example:

    measured       when delivered_cells > 0
    no_deliveries  when authored_cells > 0 and delivered_cells == 0
    no_attacks     when authored_events == 0

Keep the numeric fields for backwards compatibility, but use the status in
plots and captions. This is especially important for method comparisons where
trust may stop an attacker from reaching a victim while another method receives
the reports.

7. Diagram/reporting defects found in visual inspection -- CONFIRMED
--------------------------------------------------------------------

The PNG files can be generated successfully while still being misleading.
The current plot_manifest only records exceptions and does not validate that a
plot contains the expected series or that annotations fit inside the axes.
The following issues were reproduced by inspecting the harmonized smoke
output and tracing the corresponding plotting code.

7.1 Fake-obstacle series is omitted from 02_fake_claim_influence.png

The new timeseries schema stores fake-obstacle values in:

    active_fake_claim_count
    influential_fake_claim_count

But reporting.py constructs the type name as fake_obstacle and checks for:

    active_fake_obstacle_claim_count
    influential_fake_obstacle_claim_count

Because false-clearance/stale columns are present, the legacy fallback is not
used. The resulting plot for a fake-only or mixed run displays only the false
clearance and stale-reassertion legend entries, even when the CSV contains
nonzero fake-obstacle claims. This is a confirmed visualization bug, not a
simulation discrepancy.

Fix:

  - map attack type fake_obstacle explicitly to the schema suffix fake;
  - keep false_clearance and stale_reassertion mappings explicit;
  - add a plotting test that supplies nonzero fake, false-clearance, and stale
    columns and asserts that all three labels/series are rendered; and
  - add a plot-manifest warning if an authored attack type has no corresponding
    plotted series.

7.2 The stored-claim panel only plots the first benign robot

In the same function, the upper panel uses benign[0] as its reference series.
The lower panel loops over all benign robots. If only R2 has a claim, the upper
panel silently hides it. This is especially dangerous when one victim accepts
an attack and another victim rejects it.

Fix:

  - either plot one stored/unexpired line per benign robot, matching the lower
    panel, or explicitly plot a clearly labelled benign-total aggregate;
  - do not use the first benign robot as an undocumented proxy; and
  - test a case where only the second victim has an active claim.

7.3 Trust-crossing markers and the major-event timeline are disconnected from
    the actual event schema

The rollout writes trust events as kind=trust_update with recipient_id,
old_trust, new_trust, and outcome. The trust plot and event timeline search
  only for attacker_distrusted and attacker_retrusted events, which are not
  emitted in the current events.csv files. Therefore:

  - 01_attacker_trust_over_time.png shows the trust curves and legend but no
    distrust/retrust markers, even when the summary reports a threshold
    crossing; and
  - 07_event_timeline.png is blank except for phase shading when there are no
    traffic deadlock events, even when trust threshold crossings occurred.

The underlying summary is not wrong: an independent audit found zero
mismatches between time_to_distrust_by_robot and the first trust_update below
the configured threshold across the current smoke and partial outputs.

Fix:

  - derive markers from trust_update rows by detecting threshold crossings;
  - use recipient_id to assign each marker to the correct benign robot;
  - label the timeline row as a trust transition; and
  - write an explicit "no major events" annotation when a timeline really has
    no trust or deadlock events.

7.4 A3 security/performance plot clips the highest point and overlaps labels

The current A3 y-limit calculation makes the upper limit equal to the maximum
observed y value in common cases. The marker at the maximum is therefore
clipped by the axes boundary. In the Room 32 mixed smoke plot, Trust-fused is
at approximately 115.6 steps and its marker is visibly cut off at the top.
Full trust and Majority vote also have nearly coincident x values, so their
labels overlap.

Fix:

  - add positive headroom based on marker size and label offsets, e.g. compute
    the domain from all point coordinates plus a minimum padding rather than
    setting the upper limit to the data maximum;
  - use collision-aware or deterministic alternate label offsets when points
    are within a small distance; and
  - add a visual regression test that checks every point lies strictly inside
    the data limits and that the four labels have distinct bounding boxes.

7.5 Traffic-health plot omits completed-yield count

The summary contains traffic_yields_completed, but 08_traffic_health.png
plots yield episodes, deadlocks, conflicts, and recoveries without plotting
traffic_yields_completed. In runs such as default/fake/seed 1/full_trust, the
figure shows 12 yield episodes and 11 deadlock recoveries but gives no direct
completed-yield value. This makes the traffic accounting harder to reconcile.

Fix:

  - include completed yields as a separate bar; and
  - keep the definitions distinct: yield episodes started, yield episodes
    completed, deadlock episodes detected, and deadlock episodes recovered.

These diagram issues do not change the simulation outputs, but they must be
fixed before using the figures as evidence. Plot generation success alone is
not sufficient.

    full manifest mismatch:       0

The partial post-harmonization directory also has no manifest mismatch in its

The exact paired fields were checked for event ID, attack type, step, cell
coordinates, claim, obstacle episode, sender, recipients, observation step,
authored event count, authored cell count, actual malicious actions, phase
length, map hash, and scenario manifest hash. Delivered/accepted/influential
counts are allowed to differ by method because those are defense outcomes;
authored attack locations and dosage are not.

Additional movement and metric invariants also passed on the 48-run smoke:

  - robot action records cover every step for every robot;
  - no action jumps more than one grid cell;
  - no action is outside the map or on a static obstacle;
  - no same-step robot overlap occurs;
  - trust/source-memory values remain within [0, 1];
  - delivery/replan/path/no-path counters do not decrease;
  - authored, delivered, accepted, and influential malicious-report
    denominators reconcile exactly; and
  - reported distrust times match trust-update threshold crossings.

This means the current evidence does not show a method-specific attack
injection bug. The remaining concern is that the diagrams can fail to display
correctly even when their underlying CSVs are correct.


9. Reporting fixes implemented
-------------------------------

The reporting-layer fixes described in section 7 are now implemented in
map_poisoning/reporting.py:

  - trust thresholds are loaded from effective_config.json when they are not
    repeated in robot_timeseries.csv;
  - current trust_update rows are converted into distrust/retrust threshold
    crossings using recipient_id, old_trust, and new_trust;
  - fake-obstacle columns use the simulator's active_fake_claim_count and
    influential_fake_claim_count names;
  - stored-claim plots include every benign robot and only attack types
    authored by the run when the manifest provides that information;
  - traffic_yields_completed is shown separately from yield episodes;
  - A3 has explicit upper headroom and deterministic spacing for nearby
    labels; and
  - report_summary.txt uses the same normalized trust-crossing events.

Regression coverage was added for current trust-update events and the legacy
fake-claim schema. The reporting tests pass (14/14), and the complete suite
passes (182/182). Existing harmonized smoke artifacts were regenerated; all
six aggregate plot manifests report zero plotting failures.
