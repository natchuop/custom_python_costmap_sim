1. SCIENTIFIC GOAL
==================

The simulator studies malicious shared-map misinformation in cooperative robot
navigation. The experiment is intended to test whether different fusion/trust methods
retain or suppress malicious information differently, and whether those differences
produce navigation consequences.

Desired causal chain:

    malicious information remains operational
        -> wrong/expensive map belief
        -> route changes, detours, no-path, backtracking, or delayed shortcuts
        -> longer delivery cycles / lower efficiency

Do NOT tune the simulator simply to force Source Memory to win.
Do NOT give one defense a different planner/replan policy.
Do NOT select attacks using a tested defense method's future route.


2. PRIMARY METHODS
==================

The four primary experimental methods remain exactly:

    1. majority_vote
    2. full_trust
    3. trust_fused
    4. source_memory

Optional/diagnostic methods may remain in the code but are not part of the primary
comparison.


3. DEFAULT EXPERIMENT TIMELINE
==============================

Default phases:

    reconnaissance = 500 steps       steps 0..499
    attack          = 2000 steps      steps 500..2499
    recovery        = 500 steps       steps 2500..2999
    total           = 3000 steps

No new malicious attacks should be injected during recovery.

For targeted development experiments, 1000-step runs are appropriate:

    500 recon + first 500 attack steps

This is the preferred first validation horizon after reconnaissance/attack-authoring
changes. Do not jump directly to large multi-seed 3000-step experiments until the
focused behavior is correct.

5. GLOBAL FAIRNESS / SAFETY INVARIANTS
======================================

Preserve all of the following:

- Same planner rules for all four methods.
- Same replanning rules for all four methods.
- Same physical-world rules for all four methods.
- One shared scenario/attack manifest per map + seed + attack condition.
- Replay that exact manifest across all four methods.
- Direct LiDAR observation remains authoritative.
- Directly observed physical BLOCKED cells are hard planner walls while valid memory
  remains, unless legitimately superseded according to existing rules.
- blocked_probability_threshold remains 0.60.
- Bayesian confirmation multiplier remains 0.05.
- contradiction multiplier remains 6.0.
- distrust threshold remains 0.50.
- Source Memory recovery rate remains 0.05.
- No fourth robot.
- No attack-specific planner sensitivity.
- No defense-specific attack placement.
- Fake Obstacle footprints must remain physically free.
- False Clearance targets must actually be physically BLOCKED.
- Stale Reassertion must remain tied to genuinely cleared TEMPORARY obstacles.
- Stale Reassertion must retain the historical/pre-clearance observation timestamp.
- Stale Reassertion must not target permanent obstacles.
- Stale target age window remains 30..100 steps.
- Distinct/no-repeat stale cleared-episode behavior remains.
- Recovery phase receives no new malicious attack injections.


6. STRICT RECONNAISSANCE-ONLY ATTACK KNOWLEDGE RULE
===================================================

This is now a hard architecture rule, not a recommendation.

ATTACK RELEVANCE / TARGET RANKING MAY USE ONLY:

- static map/environment geometry;
- scenario constants known before the run;
- the clean attack-free reconnaissance rollout from steps 0..499;
- data derived exclusively from those reconnaissance observations;
- pre-authored scenario/physical-obstacle schedule only where required to establish
  semantic eligibility (for example, whether a temporary obstacle has in fact cleared).

AFTER STEP 499, ATTACK AUTHORING MUST NOT LEARN OR USE:

- robot positions;
- current/future robot goals;
- tested robot paths;
- clean-reference future paths;
- post-recon traffic;
- post-recon visibility/LiDAR history;
- post-recon mission choices;
- post-recon delivery state;
- defense-specific belief/trust/planner information.

Important distinction:

The runtime may still verify that a target is semantically eligible at an attack step
(e.g. a temporary obstacle really has cleared before Stale Reassertion is injected).
That is a physical-truth validity check, NOT an attack-relevance signal. It must not be
used to make a target more attractive because of where robots are after recon.

Required regression concept:

    Two scenarios identical through reconnaissance but radically different afterward
    must produce the same frozen attack scores/target ordering/manifest authoring
    decisions, except for validity constraints that are part of the fixed scenario
    schedule.


7. CURRENT PHYSICAL / PLANNER STATE
===================================

Current reviewed physical-obstacle defaults:

    3 permanent runtime physical obstacles
    6 concurrent/moving temporary physical obstacles

Do not casually revert to older 2+5 settings.

Key planner fixes that must remain:

1. Known physical BLOCKED cells remain hard walls while direct/local memory is valid.
2. Probabilistic methods use the same operational 0.60 blocked threshold.
3. All methods share periodic route optimization/reconsideration.
4. False Clearance uses the common improvement-only A* shortcut reconsideration when a
   newly accepted FREE report can reveal a shorter route.
5. Current direct LiDAR cannot be overridden by malicious peer information.

A historical regression test in the uploaded code expected directly observed physical
BLOCKED memory to soften before expiration. That expectation contradicted the current
hard-wall invariant and already failed in the untouched uploaded archive. The latest
code updates that test to verify that the cell remains infinite cost through step 299
and becomes unknown/traversable only after the 300-step memory expiration.


8. ATTACKS - CURRENT STATUS
===========================

8.1 Fake Obstacle
-----------------

Semantics:

    attacker reports BLOCKED on truly free space

Current status:

- operationally working;
- can cause direct path changes/detours;
- direct physical verification can contradict it and punish trust;
- current attack overlay is misinformation only, not physical collision truth.

Recent shortened regression smoke after the latest Stale/cache changes showed direct
Fake Obstacle path changes still occur. No change is currently required unless the
unified reconnaissance refactor accidentally regresses it.


8.2 False Clearance
-------------------

Semantics:

    attacker reports FREE on a real physical BLOCKED footprint

Can target permanent and active temporary obstacles according to existing semantics.
The important common improvement-only A* shortcut replan fix is already implemented.

Current status:

- strong on default map;
- measurable but weaker on room-32;
- regression smoke after the latest Stale/cache changes still produced direct False
  Clearance path changes.

Do not modify its planner behavior in this pass. Give it access to the same improved
frozen recon representation as every attack.


8.3 Stale Reassertion
---------------------

Semantics MUST remain:

- temporary obstacles only;
- obstacle must genuinely have cleared;
- replay the old BLOCKED report;
- retain the original/pre-clearance historical observation timestamp;
- report may therefore be historically truthful but operationally obsolete;
- later FREE observation must not automatically be treated as proof that the source
  lied at the original timestamp.

This means Stale Reassertion should generally be trust-neutral with respect to a truly
historical report: it should not receive artificial positive trust simply for replaying
it, and it should not receive Fake-Obstacle-style punishment merely because the world
changed later.

Its intended navigation effect is still direct:

    obsolete BLOCKED belief
        -> victim avoids a corridor that is physically free now
        -> route change/detour/no-path/extra path length

If Stale only preserves trust but never changes navigation, it is too weak as a
standalone attack.

==================================================

The current latest code includes the first Stale relevance improvement.

Warehouse/default authoring:

- computes a recon-derived stale reblock penalty using recon-observed mission states;

- existing traffic/bottleneck/detour/freshness relevance still ranks within the class;

It deliberately gives the zero-penalty candidate a very large traffic advantage and
verifies that the candidate with genuine positive mission reblock penalty still wins.

11. CURRENT ARCHITECTURAL PROBLEM TO FIX NEXT
=============================================

The default warehouse authoring and generic MovingAI authoring do NOT yet obtain their
recon information through the same rich real-rollout representation.

The default path has richer recon-observed robot state/mission information.
The generic MovingAI path still relies substantially on fixed/nominal starts, targets,
nominal route corridors, and synthetic/derived mission geometry.

This violates the desired architectural principle:

    only the environment/map should change from map to map;
    the reconnaissance and attack-authoring process should otherwise be the same.

The NEXT implementation should eliminate that difference.

=========================

At minimum collect the following from benign robots during steps 0..499:

A. Cell traffic

    traffic_heatmap[cell] += observed benign robot occupancy/usage

B. Position -> goal mission snapshots

For each benign robot at useful intervals/events:

    step
    robot_id
    current position
    current goal
    mission/delivery identifier

C. Actual/planned route snapshots

Store enough route information to answer:

- how many recon route snapshots use/approach it?

D. Temporary obstacle reopen evidence

For temporary obstacles that appear/clear during recon, record enough to determine:

Retain recon-only visibility information needed by Fake Obstacle delayed-verification
or other current relevance calculations.

Do not continue updating any of these structures after step 499.


16. STALE REASSERTION - NEXT TARGETING UPGRADE
==============================================

The next Stale scorer should answer a stronger question than the current generic
MovingAI implementation:

    Did reconnaissance demonstrate that robots actually benefit when this old temporary
    footprint is FREE?

For every stale candidate footprint F, evaluate many recon mission snapshots.

For each snapshot (position, goal):

    free_path    = A*(position, goal, footprint F free)
    blocked_path = A*(position, goal, footprint F blocked)

Only compare when both are finite.

    penalty = blocked_path_length - free_path_length

Collect candidate features such as:

    max_reblock_penalty
    mean_positive_reblock_penalty
    affected_route_snapshot_count
    affected_mission_count
    distinct_robot_count
    route_capture_count
    route_near_capture_count
    post_clear_usage_count
    reopen_benefit_count
    recon_traffic_near_footprint
    bottleneck_score
    finite_detour_score

Definitions:

route_capture_count:
    number of frozen recon free-route snapshots whose path directly intersects the old
    footprint.

route_near_capture_count:
    number of relevant recon routes within approximately 1 free-space cell of the
    footprint when direct intersection is too strict.

affected_mission_count:
    number of distinct recon missions for which blocking the footprint creates positive
    finite extra cost.

reopen_benefit_count:
    count/indicator that reconnaissance actually observed the corridor becoming more
    useful after the temporary obstacle cleared.

post_clear_usage_count:
    how often frozen recon routes/robot traffic use the reopened footprint/corridor
    after its clearance during reconnaissance.


17. USE TIERED / LEXICOGRAPHIC STALE SELECTION
==============================================

Do NOT rely only on one giant multiplied score where high traffic can overpower actual
mission consequence.

Recommended candidate tiers, strongest first:

TIER 1
    observed recon reopen benefit
    AND positive finite reblock penalty

TIER 2
    recon free route actually crosses/uses footprint
    AND positive finite reblock penalty

TIER 3
    positive finite reblock penalty for recon mission snapshots

TIER 4
    generic recon traffic/bottleneck/detour relevance only

Choose from the highest non-empty tier.

Within a tier, rank roughly by:

    affected_mission_count
    distinct_robot_count
    route_capture_count
    mean/max reblock penalty
    route recurrence
    post-clear usage
    traffic
    bottleneck/detour
    freshness within the existing 30..100 window

A conceptual ordering tuple is preferable to opaque coefficient tuning:

    (
        tier,
        affected_mission_count,
        route_capture_count,
        distinct_robot_count,
        mean_positive_reblock_penalty,
        max_reblock_penalty,
        post_clear_usage_count,
        traffic_score,
        bottleneck_score,
        freshness,
    )

Exact ordering may be adjusted if deterministic tests reveal pathological behavior, but
the first principle should remain:

    proven recon mission consequence > generic popularity/traffic

Do NOT lower the stale age window to 10..60. That was already tested and rejected.


18. APPLY THE SAME RICHER RECON DATA TO ALL ATTACKS
===================================================

The richer FrozenReconData must not become a Stale-only privilege.

Fake Obstacle can use the same frozen data for:

- actual recon route overlap;
- recurrent corridor use;
- distinct mission/robot usage;
- traffic;
- bottleneck/detour relevance;
- recon-only delayed direct-verification preference.

False Clearance can use the same frozen data for:

- actual recon mission shortcut gain when removing a real obstacle;
- route overlap;
- recurrent mission use;
- traffic/bottleneck relevance.

Stale Reassertion can use it for:

- reopened route benefit;
- recurrent usage of cleared corridors;
- finite reblock penalties;
- affected missions/robots.

Each attack can use different scoring semantics, but every score must be computed from
the same frozen reconnaissance knowledge boundary.

24. STALE SUCCESS CRITERIA
==========================

The immediate goal is not to force every stale event to trigger a replan.

A good development result should show:

- direct stale_reassertion_path_changes > 0 on BOTH default and room-32 in at least some
  method/seed combinations;
- broader attack-induced path changes remain or increase;
- measurable route-affected steps and/or extra path length;
- no physical collision regression;
- no stale-specific planner logic;
- no unfair trust collapse from a historically truthful old observation;
- no artificial trust boost merely because a stale report was replayed;
- Source Memory / Trust Fused can suppress operational malicious influence according to
  their existing trust semantics;
- shared-manifest fairness passes;
- candidate ranking is demonstrably based on frozen recon information only.

If default improves but room-32 remains zero, inspect the actual frozen recon feature
coverage before changing trust, age windows, or planner rules.

Questions to ask first:

- Did room-32 recon observe enough distinct missions?
- Did any temporary obstacle clear during recon in a route-relevant corridor?
- Are positive finite reblock candidates present?
- Are recurrent-use candidates present but losing to a weaker score?
- Is route_capture too strict and should 1-cell near-capture be used as a secondary tier?
- Are temporary obstacle placements themselves rarely intersecting useful room-32
  corridors?

Only after answering those should candidate-placement logic be refined.

27. PERFORMANCE / TIMEOUT HANDLING
==================================

Some warehouse authoring/test combinations are expensive and may exceed wrapper limits.

If a test or experiment times out:

1. Check whether the process reached simulation completion but stalled in reporting/CSV
   generation.
2. Run one method per fresh process instead of keeping many large rollout/log objects in
   one interpreter.
3. Serialize the manifest once, then replay it from disk for each method.
4. Run pytest by file/group rather than one monolithic command.
5. Record TIMEOUT separately from FAIL.
6. Do not reduce scientific settings merely to hide a performance regression unless the
   run is explicitly a smoke test.
7. For smoke tests, shortened phase horizons are acceptable, but label them clearly and
   never present them as production/default results.

If authoring suddenly becomes much slower after FrozenReconData changes:

- profile candidate scoring;
- cache A* free/blocked route evaluations by (snapshot, footprint) where safe;
- pre-index routes/cells to avoid evaluating obviously irrelevant candidates;
- do not cache across attack types unless the cached quantity is truly attack-neutral;
- retain attack_type in attack-specific relevance cache keys.


28. ERROR / BUG TRIAGE PROCEDURE
================================

When any new error appears:

STEP 1 - Reproduce minimally
    Use one map, one seed, one attack, one method if possible.

STEP 2 - Classify

    syntax/import error
    deterministic test failure
    semantic invariant failure
    manifest mismatch
    route/planner regression
    trust-verification regression
    performance/timeout
    output/reporting-only issue

STEP 3 - Compare with baseline
    If uncertain, run the same minimal case on the untouched uploaded package.

33. FINAL DESIGN PRINCIPLE
==========================

The simulator should not have a "warehouse attack process" and a separate "MovingAI
attack process" with different intelligence quality.

It should have:

    ONE reconnaissance process
    ONE frozen reconnaissance knowledge boundary
    ONE attack-authoring framework
    ONE planner/replan framework
    ONE shared-manifest replay process

with the map/environment as the changing variable.

Stale Reassertion should become more impactful because reconnaissance identifies old
obstacle footprints whose reopening was demonstrably important to real benign missions,
not because Stale receives future information or because the victim planner is made
more sensitive specifically to Stale.
